# Task 004: Generate Golden Files for Audio Tags (M-2.0)

## Objective
Write a Python script that dumps all audio tags from the test data files as JSON golden files, to be used for verifying the Rust audio tag reader produces identical output.

## Context
Rose is a music library manager being migrated from Python to Rust. The audio tag reading layer is the highest-risk component (data corruption potential). Golden files capture the exact Python output so the Rust implementation can be validated byte-for-byte against it.

## Constraints Relevant to This Task
- **Audio tag structure is frozen.** The on-disk tags (roseid, rosereleaseid, genre encoding with `;` delimiters, artist role encoding, `\\PARENTS:\\` genre delimiter, etc.) are the source of truth.
- This is a **Python-only task** — no Rust code is written.
- Golden files must cover all 5 formats: FLAC, MP3, M4A, OGG Vorbis, OGG Opus.

### 2. Write a Python script `scripts/generate_tag_golden_files.py`
The script should:
1. Import `rose.audiotags.AudioTags`.
2. Iterate over all audio files in `testdata/Tagger/` (or wherever the test audio files live).
3. For each file, call `AudioTags.from_file(path)`.
4. Serialize the `AudioTags` instance to a JSON dict with ALL fields:
   - `id`, `release_id`
   - `tracktitle`, `tracknumber`, `tracktotal`, `discnumber`, `disctotal`
   - `trackartists` (serialized as `{"main": [{"name": "...", "alias": false}], ...}`)
   - `releasetitle`, `releasetype`, `releasedate` (as string), `originaldate`, `compositiondate`
   - `genre`, `secondarygenre`, `descriptor`, `label`
   - `edition`, `catalognumber`
   - `releaseartists` (same format as trackartists)
   - `duration_sec`
   - `path` (relative to repo root)
5. Write one JSON file per format: `tags_flac.json`, `tags_mp3.json`, `tags_m4a.json`, `tags_ogg_vorbis.json`, `tags_ogg_opus.json`. Each file contains a list of tag dumps for all files of that format.
6. Sort keys in JSON output for determinism. Use `indent=2` for readability.

### 3. Also dump raw custom tag values

### Quirks in Test Data
- **No ROSEID/ROSERELEASEID set:** All test files have `id: null` and `release_id: null`. These custom Rose tags are not pre-populated in the test fixtures (they get written during library import). The Rust port should expect null for these in the golden files.
- **Multi-value artist tags in M4A/Vorbis/Opus:** Artist roles (remixer, producer, composer, conductor, djmixer) are stored as separate tag values per artist in M4A and Vorbis/Opus, but as a single semicolon-delimited string in the `artist` tag after Rose processing. The `trackartists` field in the golden output reflects the *parsed* artist mapping, not the raw tag layout.
- **MP4 tracknumber/discnumber are integers:** M4A stores track/disc as integer tuples `(number, total)`, but `AudioTags` converts them to string representation (e.g., `"2"`).
- **Duration rounding:** Duration is `round(m.info.length)` which gives 2 sec for FLAC/M4A and 1 sec for MP3/Vorbis/Opus (the files are all ~2 seconds long, rounding varies by codec).

### Golden File Format
Each golden file is a JSON array of objects. Each object has these top-level keys (sorted):
- `catalognumber`, `compositiondate`, `descriptor`, `discnumber`, `disctotal`, `duration_sec`, `edition`, `genre`, `id`, `label`, `originaldate`, `path`, `raw_custom_tags`, `release_id`, `releaseartists`, `releasedate`, `releasetitle`, `releasetype`, `secondarygenre`, `trackartists`, `tracknumber`, `tracktitle`, `tracktotal`

The `trackartists` and `releaseartists` fields are objects with keys: `main`, `guest`, `remixer`, `producer`, `composer`, `conductor`, `djmixer`. Each is a list of `{"name": "...", "alias": false}`.

The `raw_custom_tags` field contains the raw (pre-parsing) custom tag values:
- For **FLAC/Vorbis/Opus**: Vorbis comment key → list of string values
- For **MP3**: ID3 TXXX frame key → list of string values
- For **M4A**: MP4 freeform atom key → list of `{"decoded": "...", "base64": "..."}` (raw bytes as base64)
