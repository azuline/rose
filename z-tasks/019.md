# Task 019: Parallel Cache Update with Rayon (M-7.2)

## Objective
Add rayon-based parallelism to the cache update pipeline so that multiple release directories are processed concurrently, with each worker opening its own SQLite connection and errors collected rather than aborting.

## Context
Rose is a music library manager being migrated from Python to Rust. The Python version uses `multiprocessing.Pool` to parallelize release processing. In Rust, we use rayon. The key architectural decision: each rayon worker opens its own `rusqlite::Connection` (WAL mode + busy_timeout enable concurrent reads). Workers return data structures; the main thread performs all SQL writes in a single transaction.

## Constraints Relevant to This Task
- SQLite PRAGMAs (WAL, foreign_keys, busy_timeout=15s) on every connection — this is what makes concurrent access safe.
- Each rayon worker opens its own connection. Workers do NOT share connections across threads.
- Workers return `Result`. Errors are collected into a `Vec` and reported after all valid work completes. One corrupt directory must NEVER abort the entire cache update.
- Parallelism threshold: only parallelize when >= 50 release directories (matching Python). Below 50, run single-threaded.
- Number of threads: use `config.max_proc`, but reduce if `release_dirs.len() < max_proc * 50`.
- After parallel processing, the main thread does all SQL writes (from task 018's `batch_write_releases`).
- After release writes, collage/playlist updates run on the main thread (they are few and not worth parallelizing).

### 2. Modify `update_cache_for_releases`
```rust
pub fn update_cache_for_releases(
    config: &Config,
    release_dirs: Option<Vec<PathBuf>>,
    force: bool,
) -> Result<()>
```

Logic:
- Scan directories (stage 1 — always single-threaded, fast).
- If scanned.len() < 50 → run stages 2-4 sequentially on main thread (current behavior).
- If scanned.len() >= 50:
  - Compute `num_workers = min(config.max_proc, max(1, scanned.len() / 50))`.
  - Partition `scanned` into chunks.
  - Use `rayon::ThreadPoolBuilder::new().num_threads(num_workers).build()` to create a scoped pool.
  - Each worker runs: `detect_changes` → `read_tags_and_derive_metadata` → `rename_source_files` on its chunk.
  - Workers return `Result<Vec<PreparedRelease>>`. Use `rayon::iter::ParallelIterator` with `.map()` and collect results.
  - Collect errors and successes separately.
  - Log all errors but continue with successful results.
- Main thread: flatten all `Vec<PreparedRelease>` from workers → `batch_write_releases` (stage 5).
- Main thread: update affected collages/playlists.
- If there were errors, return them as a combined error (or log and continue — match Python's `ExceptionGroup` behavior).

### 3. Error handling pattern
```rust
let results: Vec<Result<Vec<PreparedRelease>>> = pool.install(|| {
    chunks.par_iter().map(|chunk| {
        // Each worker: stages 2-4
        let candidates = detect_changes(config, chunk, force)?;
        let mut prepared = read_tags_and_derive_metadata(config, candidates)?;
        rename_source_files(config, &mut prepared)?;
        Ok(prepared)
    }).collect()
});

let mut all_prepared = Vec::new();
let mut errors = Vec::new();
for result in results {
    match result {
        Ok(prepared) => all_prepared.extend(prepared),
        Err(e) => errors.push(e),
    }
}
// Log errors, proceed with all_prepared
```
