# Task 048: Benchmark Python vs Rust (M-15.2)

## Objective
Measure performance of key operations in both the Python and Rust implementations, compare them, and produce a benchmark results document at `z-thinking/benchmark-results.md`.

## Context
Rose is a music library manager that has been migrated from Python to Rust for performance reasons (the author stated Python is "too unperformant for a virtual filesystem"). This task quantifies the improvement by benchmarking identical operations in both implementations.

## Constraints Relevant to This Task
- Use `testdata/` or a synthetically generated larger library for benchmarking.
- For meaningful VFS benchmarks, FUSE must be available (may not work in CI).
- Measure wall-clock time. Use `hyperfine` for CLI benchmarks if available, otherwise shell `time`.
- Run each benchmark multiple times (at least 5) and report mean ± stddev.
- The Python implementation must still be functional (this task runs BEFORE task 051 deletes it).

## Prior Work
- **Python CLI:** Invoked via `rose` command (Python entry point from `rose-cli`).
- **Rust CLI:** Built from `rose-rs/rose-cli/`, binary at `rose-rs/target/release/rose`.
- **Test data:** `testdata/` contains 3 releases with 2 tracks each (6 total audio files), 1 collage, 1 playlist.

## Files to Read
- `testdata/` (directory structure — to understand data size)
- `rose-rs/rose-cli/src/main.rs` (Rust CLI subcommands)
- `rose-cli/rose_cli/cli.py` (Python CLI subcommands — to invoke matching operations)
- `flake.nix` (to verify both toolchains are available in dev shell)

## What to Implement

Create `rose-rs/benches/benchmark.sh` (or a suitable benchmarking script):

1. **Setup:**
   - Create a temp directory, copy `testdata/` as the music source.
   - Write a config TOML for each implementation (paths may differ).
   - Build the Rust binary in release mode: `cargo build --release -p rose-cli`.
   - Verify both `rose` (Python) and the Rust binary are available.

2. **Benchmarks to run:**

   **a. Cache update (cold start — empty cache):**
   - Delete cache, then `rose cache update`. Measure wall-clock time.
   - Run for both Python and Rust, 5+ iterations each.

   **b. Cache update (warm — no changes):**
   - Run `rose cache update` when cache is already up-to-date.
   - Measures mtime comparison overhead.

   **c. List all releases (JSON output):**
   - `rose releases print-all` — measures cache read + serialization.

   **d. List all tracks (JSON output):**
   - `rose tracks print-all` — larger output, more joins.

   **e. Cold start time (help/version):**
   - `rose version` — measures binary startup overhead.

   **f. VFS readdir latency (if FUSE available):**
   - Mount VFS, then `ls -la <mount_point>/Releases/`.
   - Measure with `time`. Compare Python vs Rust mount + readdir.

3. **For larger-scale benchmarks** (optional but recommended):
   - Create a synthetic library by copying `testdata/` releases N times with unique UUIDs.
   - Benchmark cache update for 10, 50, 100 releases.
   - This shows scaling behavior.

4. **Output:** Write results to `z-thinking/benchmark-results.md` in a table format:

   ```markdown
   # Benchmark Results: Python vs Rust

   ## Environment
   - Hardware: ...
   - Date: ...
   - Testdata: N releases, M tracks

   ## Results

   | Operation | Python (mean ± std) | Rust (mean ± std) | Speedup |
   |-----------|--------------------|--------------------|---------|
   | Cache update (cold) | ... | ... | ...x |
   | Cache update (warm) | ... | ... | ...x |
   | List releases | ... | ... | ...x |
   | ...        | ... | ... | ...x |
   ```
