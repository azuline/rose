# Task 016: Cache Update — Tag Reading and Metadata Derivation (M-7.1c)

## Objective
Implement stage 3 of the cache update pipeline: read audio tags from changed tracks, derive release-level metadata from the first track, assign/persist track IDs, and produce fully enriched release/track data structures ready for SQL writes.

## Context
Rose is a music library manager being migrated from Python to Rust. After mtime comparison (stage 2) identifies changed files, this stage reads their audio tags and derives the release metadata. Release-level fields (title, type, date, genres, artists, etc.) come from the first audio track's tags.

**Pipeline overview:**
1. Task 014: Scan directories → `Vec<ScannedRelease>`
2. Task 015: Compare mtimes → `Vec<CacheCandidate>`
3. **This task (016):** Read tags, derive metadata → `Vec<PreparedRelease>`
4. Task 017: Rename directories
5. Task 018: Batch SQL writes

## Constraints Relevant to This Task
- Release metadata is derived from the FIRST audio file's tags (release title, type, dates, genres, artists, etc.).
- Track IDs and release IDs are written to audio files via `AudioTags::flush()` if missing or mismatched — this mutates source files.
- After writing IDs, the track mtime must be re-read (since the file was modified).
- `tracknumber` and `discnumber` have `.` characters stripped (VFS uses `.` as separator).
- `tracktotal` is computed per-disc (count of tracks sharing the same `discnumber`).
- `disctotal` is count of distinct disc numbers.
- Duplicate track IDs within a release → `DuplicateTrackError`.

### Functions

1. **`read_tags_and_derive_metadata(config, candidates: Vec<CacheCandidate>) -> Result<Vec<PreparedRelease>>`**

   For each `CacheCandidate`:
   a. Track the first audio file where tags are read (`pulled_release_tags` flag).
   b. For each `TrackCandidate`:
      - If `needs_read=false` and cached exists → reuse cached Track, count towards totals.
      - If `needs_read=true`:
        - Call `AudioTags::from_file(path)`. Handle `FileNotFoundError` → skip with warning.
        - On the first tag read, extract release-level fields and compare to cached release. If any differ → `release_dirty = true`. Update release fields. Apply `uniq()` to genre/descriptor/label lists. Compute `parent_genres` and `parent_secondary_genres`.
        - Assign track ID: if `tags.id` is None or `tags.release_id` doesn't match → set and call `tags.flush(config)`. Re-read mtime after flush.
        - Build `Track` struct. Strip `.` from tracknumber/discnumber.
        - Check for duplicate track IDs → return `DuplicateTrackError`.
   c. After all tracks: compute per-disc `tracktotal` (counter by discnumber), `disctotal` (distinct discnumber count). Update tracks and release if totals changed.
   d. Compute `metahash` for release and each dirty track (SHA-256 of relevant fields, matching Python's `sha256_dataclass`).
   e. Build `PreparedRelease`.

### Data flow to next stage
`Vec<PreparedRelease>` is passed to task 017 (renaming). Each entry has a fully populated `Release` and `Vec<Track>` plus flags indicating what needs SQL writes.

### Metahash implementation

Two private helper functions compute SHA-256 metahashes:

- **`sha256_release_metahash(r: &Release) -> String`**: Hashes a serializable subset of release fields (all metadata fields except `metahash`, `source_path`, `cover_image_path`, `datafile_mtime`). Uses an intermediate `ReleaseHashable` struct with alphabetically-sorted fields for deterministic serialization via `serde_json`, then SHA-256 hashes the JSON.

- **`sha256_track_metahash(t: &Track) -> String`**: Hashes track-level metadata fields (`id`, `tracktitle`, `tracknumber`, `tracktotal`, `discnumber`, `duration_seconds`, `trackartists`). Uses an intermediate `TrackHashable` struct with the same approach.

Both use `crate::common::sha256_struct()` internally (JSON serialization + SHA-256).

### Key decisions

- **Release fields from first track**: The `pulled_release_tags` flag ensures release-level metadata is extracted from only the first track whose tags are actually read (matching Python's behavior).
- **Sidecar data application**: `stored_data` fields (new/favorite/rating/added_at) are applied to the release before tag reading. `added_at` is only set if the release doesn't already have one (for new releases).
- **Track ID assignment logic**: Matches Python exactly — if `tags.id` is None OR `tags.release_id` doesn't match the sidecar's release ID, both are set and flushed. After flush, mtime is re-read.
- **Error handling for file reads**: `UnsupportedFiletype` errors are logged as warnings and skipped. If the file doesn't exist at read time, it's skipped with a warning. Other errors are propagated.
- **`tracktotal` per disc**: Uses a `HashMap<String, i32>` counter keyed by discnumber. After all tracks are processed, each track's tracktotal is updated if it differs from the counter, and that track is added to `track_ids_to_insert`.
- **`_config` parameter**: The config parameter is prefixed with underscore since it's not used in stage 3 (will be needed in later stages for rename templates, etc.), but is kept in the signature for API consistency.
