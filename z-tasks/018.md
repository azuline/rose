# Task 018: Cache Update — Batch SQL Writes (M-7.1e)

## Objective
Implement stage 5 of the cache update pipeline: batch SQL writes for releases/tracks, plus the full `update_cache_for_collages`, `update_cache_for_playlists`, and eviction functions. Also wire all 5 stages into the top-level `update_cache` function.

## Context
Rose is a music library manager being migrated from Python to Rust. This is the final stage of the cache update pipeline. It takes the enriched, possibly-renamed release data from prior stages and writes everything to SQLite. It also handles collages and playlists, which write back to source TOML files on disk (not read-only!).

**Pipeline overview:**
1. Task 014: Scan directories → `Vec<ScannedRelease>`
2. Task 015: Compare mtimes → `Vec<CacheCandidate>`
3. Task 016: Read tags → `Vec<PreparedRelease>`
4. Task 017: Rename directories → mutated `Vec<PreparedRelease>`
5. **This task (018):** Batch SQL writes + collages/playlists + top-level orchestrator

## Constraints Relevant to This Task
- `update_cache_for_collages` and `update_cache_for_playlists` WRITE to source TOML files on disk (description_meta regeneration, missing flags). This is NOT read-only caching.
- Collage/playlist TOML format: `[[releases]]` / `[[tracks]]` array with `uuid`, `description_meta`, `missing` (optional) keys.
- Duplicate release IDs → `DuplicateReleaseError`.
- After release SQL writes, identify affected collages/playlists and trigger their updates.
- Eviction functions: delete from DB any releases/collages/playlists whose source paths no longer exist on disk.
- Collage/playlist dirs are created (`mkdir -p`) if they don't exist.
- SQLite PRAGMAs on every connection.
- Use `INSERT OR REPLACE` for releases/tracks (handles source_path conflicts). Use `ON CONFLICT (id) DO UPDATE` for normal updates.
- Advisory locking via `lock()` when writing to collage/playlist TOML files.

## What to Implement
Add to `rose-rs/rose-core/src/cache.rs`.

### 1. `batch_write_releases(config, prepared: &[PreparedRelease]) -> Result<(Vec<String>, Vec<String>)>`
Execute all SQL in a single connection:
- DELETE releases by empty-dir source paths.
- DELETE unknown cached tracks.
- INSERT OR REPLACE releases (with ON CONFLICT DO UPDATE).
- For each dirty release: delete + re-insert genres, secondary_genres, descriptors, labels, artists.
- INSERT OR REPLACE tracks. Delete + re-insert track artists.
- After writes, query for affected collages/playlists and return their names for forced updates.
- Returns `(collage_names_to_update, playlist_names_to_update)`.

### 2. `update_cache_for_collages(config, collage_names: Option<Vec<String>>, force: bool) -> Result<()>`
- Scan `music_source_dir/!collages/` for `.toml` files.
- Batch query existing cached collages.
- For each collage file:
  - Compare mtime (skip if unchanged and not force).
  - Read TOML, parse `[[releases]]` array.
  - Update `missing` flags (release_id not in DB → mark missing; exists → unmark).
  - Regenerate `description_meta` from DB data: `[date] artists - title`.
  - If TOML changed → write back to disk (under lock). Update mtime.
  - Upsert `collages` table, delete + re-insert `collages_releases`.

### 3. `update_cache_for_playlists(config, playlist_names: Option<Vec<String>>, force: bool) -> Result<()>`
- Same pattern as collages but with `[[tracks]]` and `playlists_tracks` table.
- Also detect cover art (file with same stem as playlist, art extension).

### 4. Eviction functions
- `update_cache_evict_nonexistent_releases(config) -> Result<()>`
- `update_cache_evict_nonexistent_collages(config) -> Result<()>`
