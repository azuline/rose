# Task 020: Cache Locking (M-7.3)

## Objective
Implement advisory locking using the `locks` SQLite table, providing mutual exclusion for concurrent cache operations on the same release, collage, or playlist.

## Context
Rose is a music library manager being migrated from Python to Rust. The locking mechanism uses SQLite's `locks` table as an advisory lock store. This prevents concurrent writes to the same `.rose.{uuid}.toml` or collage/playlist TOML file. Locks are short-lived (typically 1 second) with a polling retry loop.

## Constraints Relevant to This Task
- SQLite PRAGMAs (WAL, foreign_keys, busy_timeout=15s) on every connection.
- Locks use the `locks` table schema: `(name TEXT, valid_until REAL, PRIMARY KEY (name, valid_until))`.
- Lock acquisition: poll loop — check if existing lock has expired, if so insert new lock. On `IntegrityError` (race condition), retry.
- Lock release: `DELETE FROM locks WHERE name = ?` in a `finally`/drop block.
- Lock timeout: configurable, default 1.0 seconds (the valid_until window).
- The lock must be released even on panic (use RAII/Drop pattern).

### 2. Lock acquisition function
```rust
pub fn lock(config: &Config, name: &str, timeout: f64) -> Result<CacheLock>
```

Algorithm (matching Python):
```
loop {
    conn = connect(config)
    row = SELECT MAX(valid_until) FROM locks WHERE name = ?
    if row exists and valid_until > now():
        sleep(max(0, valid_until - now()))
        continue
    valid_until = now() + timeout
    try:
        INSERT INTO locks (name, valid_until) VALUES (?, ?)
    except IntegrityError:
        // Race condition, another process got the lock
        continue
    return CacheLock { config, name }
}
```

Use `std::time::SystemTime` for `now()` (convert to Unix epoch float). Use `std::thread::sleep` for the wait.

## Completed

### Locking API

The advisory locking system is implemented in `rose-rs/rose-core/src/cache.rs`:

- **`LockGuard`** — RAII guard struct holding a `Connection` and the lock `name`. On `Drop`, it executes `DELETE FROM locks WHERE name = ?` and logs the release. Errors in `Drop` are silently ignored (via `let _ = ...`) to avoid panics during cleanup.

- **`lock(config, name, timeout) -> Result<LockGuard>`** — Acquires an advisory lock using a poll-loop algorithm matching the Python implementation:
  1. Query `SELECT MAX(valid_until) FROM locks WHERE name = ?`
  2. If a valid (non-expired) lock exists, sleep until it expires, then retry
  3. Attempt `INSERT INTO locks (name, valid_until)` with `valid_until = now() + timeout`
  4. On unique constraint violation (race condition), retry the loop
  5. On success, return a `LockGuard` that owns the connection

- **Lock name helpers:**
  - `release_lock_name(release_id) -> "release-{release_id}"`
  - `collage_lock_name(collage_name) -> "collage-{collage_name}"`
  - `playlist_lock_name(playlist_name) -> "playlist-{playlist_name}"`

### Differences from Python

- **RAII instead of context manager**: Python uses `@contextlib.contextmanager` with `try/finally`; Rust uses `Drop` trait on `LockGuard`, guaranteeing release even on panic (unwind).
- **Connection ownership**: The `LockGuard` holds its own `Connection` rather than borrowing from `Config`, making the guard `Send` and lifetime-independent.
- **Struct naming**: Named `LockGuard` (from prior task 010) rather than `CacheLock` as the task spec suggested. The API is functionally equivalent.
