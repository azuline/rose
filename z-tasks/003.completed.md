# Task 003: Port genre_hierarchy.rs (M-1.3)

## Objective
Port the genre hierarchy data structures from Python to Rust, providing both child-to-parents and parent-to-transitive-children lookups.

## Context
Rose is a music library manager being migrated from Python to Rust. The genre hierarchy maps genres to their parent/child relationships (sourced from RateYourMusic). It's used during cache updates (genre expansion) and VFS filtering.

## Constraints Relevant to This Task
- The generator script (`scripts/rym-genres/generate.py`) already writes a JSON file for Rust consumption. Use `serde_json::from_str(include_str!(...))` to embed it at compile time.
- Data must be identical to the Python version.

## What to Implement

### 1. Locate or generate the JSON data file
The generator script writes a JSON file for Rust. Find where it's placed (likely `rose-rs/src/genre_hierarchy.json` or `rose-rs/rose-core/src/genre_hierarchy.json`). If it doesn't exist yet, run the generator or create the JSON from the Python source.

The JSON should be a map of `genre_name -> [parent_genre_1, parent_genre_2, ...]` (the `TRANSITIVE_PARENT_GENRES` direction).

### 2. Create `rose-rs/rose-core/src/genre_hierarchy.rs`

**`GENRE_HIERARCHY`** (or `TRANSITIVE_PARENT_GENRES`): `HashMap<String, Vec<String>>` — maps a child genre to its transitive parent genres. Loaded from the JSON file at startup using `LazyLock` or `once_cell::sync::Lazy`.

**`TRANSITIVE_CHILD_GENRES`**: `HashMap<String, Vec<String>>` — the inverse map: parent genre to all transitive child genres. Computed at init time by inverting `GENRE_HIERARCHY`.

Use `include_str!` to embed the JSON at compile time, then deserialize with `serde_json::from_str` in a `LazyLock`/`Lazy` initializer.

### 3. Update `lib.rs`
Add `pub mod genre_hierarchy;`

## Tests to Write
1. **Non-empty:** `GENRE_HIERARCHY` is not empty (sanity check that JSON loaded).
2. **Known entry:** `GENRE_HIERARCHY["Acid House"]` contains `"House"` and `"Electronic Dance Music"`.
3. **Inverse correctness:** If `GENRE_HIERARCHY["X"]` contains `"Y"`, then `TRANSITIVE_CHILD_GENRES["Y"]` contains `"X"`.
4. **Inverse completeness:** Every genre that appears as a parent in `GENRE_HIERARCHY` has an entry in `TRANSITIVE_CHILD_GENRES`.
5. **No self-references:** No genre maps to itself in either direction.

## Completed

### Actual Public API Created

```rust
// rose-core/src/genre_hierarchy.rs

/// Child genre → list of transitive parent genres.
pub static GENRE_HIERARCHY: LazyLock<HashMap<String, Vec<String>>>;

/// Parent genre → list of transitive child genres (inverse of GENRE_HIERARCHY).
pub static TRANSITIVE_CHILD_GENRES: LazyLock<HashMap<String, Vec<String>>>;
```

No functions — only two lazily-initialized static maps.

### Design Decisions

- **`HashMap<String, Vec<String>>` chosen over `BTreeMap`** — the primary use case is key lookup (O(1) vs O(log n)). Ordering is not needed at the map level; individual child lists within `TRANSITIVE_CHILD_GENRES` are sorted alphabetically for determinism.
- **JSON file placed at `rose-rs/rose-core/src/genre_hierarchy.json`** — co-located with the Rust source so `include_str!("genre_hierarchy.json")` works without path manipulation. The generator script originally targeted `rose-rs/src/genre_hierarchy.json` which didn't exist; the JSON was generated from the Python `TRANSITIVE_PARENT_GENRES` dict by importing the Python module directly.
- **JSON contains only the parent-genres direction** (`child → [parents]`). The `TRANSITIVE_CHILD_GENRES` inverse map is computed at first access by iterating `GENRE_HIERARCHY` and flipping the relationship. This avoids shipping redundant data in the binary and guarantees the two maps are always consistent.
- **`LazyLock` from `std::sync`** used (stabilized in Rust 1.80+), consistent with `common.rs`. No external `once_cell` dependency needed.
- **Child lists in `TRANSITIVE_CHILD_GENRES` are sorted** after inversion for deterministic iteration order and easier testing.

### Deviations from Plan

- **JSON file location differs from generator script**: the generator writes to `rose-rs/src/genre_hierarchy.json`, but since `rose-rs/src/` doesn't exist (the crate is at `rose-rs/rose-core/src/`), the JSON was placed at `rose-rs/rose-core/src/genre_hierarchy.json` instead. The generator script should be updated to match in a future task.
- **JSON was generated from Python module** rather than running the generator script, since the generator requires a `$ROSE_ROOT` environment variable and `ruff` formatter. The data is identical — extracted directly from the Python `TRANSITIVE_PARENT_GENRES` dict.

### Known Issues / Tech Debt

- **Generator script path mismatch**: `scripts/rym-genres/generate.py` writes to `rose-rs/src/genre_hierarchy.json` but the actual file lives at `rose-rs/rose-core/src/genre_hierarchy.json`. The generator should be updated to write to the correct path.
- **`IMMEDIATE_CHILD_GENRES` not ported**: The Python source also has an `IMMEDIATE_CHILD_GENRES` map (parent → direct children only). This was not requested by the task spec and is not included. It can be added later if needed for VFS directory listing.
- **Large binary size contribution**: The JSON (~225 KB) is embedded in the binary via `include_str!`. This is acceptable for a CLI tool but could be optimized with a more compact format if size becomes a concern.
