# Task 010: Cache Schema Bootstrapping (M-6.1)

## Objective
Port the SQLite cache schema bootstrapping from Python to Rust, including connection setup with correct PRAGMAs, schema creation, hash-based cache invalidation, and the advisory locking mechanism.

## Context
Rose is a music library manager being migrated from Python to Rust. The SQLite database serves as a read cache — it is derived from source files and can always be rebuilt from scratch. Schema changes trigger a full database rebuild via hash comparison.

## Constraints Relevant to This Task
- **SQLite connection setup (cross-cutting decision):** Every `rusqlite::Connection` must set on open:
  - `PRAGMA journal_mode=WAL`
  - `PRAGMA foreign_keys=ON`
  - `busy_timeout(15000)` (15 seconds, matching Python's `timeout=15.0`)
  - Autocommit mode (no implicit transactions)
- **SQLite concurrency with rayon** (future tasks): Each rayon worker opens its own connection. WAL mode and busy_timeout are required.
- Use `rusqlite` with the `bundled` feature (compiles SQLite from source) and FTS5 support.

### `connect(config: &Config) -> Result<Connection, RoseError>`
```rust
pub fn connect(config: &Config) -> Result<rusqlite::Connection, RoseError> {
    let conn = rusqlite::Connection::open(&config.cache_database_path())?;
    conn.busy_timeout(std::time::Duration::from_millis(15000))?;
    conn.execute_batch("PRAGMA journal_mode=WAL")?;
    conn.execute_batch("PRAGMA foreign_keys=ON")?;
    Ok(conn)
}
```
**Important:** Do NOT use `rusqlite::Connection::open_with_flags` with `SQLITE_OPEN_NO_MUTEX` — use default threading mode. The connection must work correctly when shared via WAL mode across threads.

### `maybe_invalidate_cache_database(config: &Config) -> Result<(), RoseError>`
1. Compute `schema_hash`: SHA-256 of the `cache.sql` file contents.
2. Compute `config_hash`: SHA-256 of JSON-serialized subset of config fields that affect cache population:
   - `music_source_dir`, `cache_dir`, `cover_art_stems`, `valid_art_exts`, `ignore_release_directories`
3. Open connection, check if `_schema_hash` table exists.
4. If it exists, compare stored `schema_hash`, `config_hash`, and `version` against computed values.
5. If all match -> return (no-op).
6. If any mismatch (or table doesn't exist) -> **delete the database file**, recreate, execute schema SQL, create `_schema_hash` table, insert computed hashes and `VERSION`.

The `_schema_hash` table:
```sql
CREATE TABLE _schema_hash (
    schema_hash TEXT,
    config_hash TEXT,
    version TEXT,
    PRIMARY KEY (schema_hash, config_hash, version)
);
```

### Advisory lock mechanism
```rust
pub fn lock(config: &Config, name: &str, timeout: f64) -> Result<LockGuard, RoseError>
```
Or use a RAII guard pattern. Behavior:
1. Check `locks` table for existing lock with `valid_until > now`.
2. If locked, sleep until lock expires, then retry.
3. Insert new lock row with `valid_until = now + timeout`.
4. On drop (or explicit release), delete the lock row.

The `locks` table is part of `cache.sql`:
```sql
CREATE TABLE locks (
    name TEXT,
    valid_until REAL NOT NULL,
    PRIMARY KEY (name, valid_until)
);
```

## Completed

### Public API Created

```rust
// rose-core/src/cache.rs

/// Open a SQLite connection with WAL, foreign_keys=ON, busy_timeout=15s.
pub fn connect(config: &Config) -> Result<rusqlite::Connection, RoseError>;

/// Ensure cache DB schema is up-to-date; deletes and recreates on hash mismatch.
pub fn maybe_invalidate_cache_database(config: &Config) -> Result<(), RoseError>;

/// RAII guard for advisory locks in the `locks` table.
pub struct LockGuard { conn: Connection, name: String }
impl Drop for LockGuard { /* deletes lock row */ }

/// Acquire an advisory lock; blocks (sleeps) if lock is already held.
pub fn lock(config: &Config, name: &str, timeout: f64) -> Result<LockGuard, RoseError>;
```

### Design Decisions

1. **rusqlite features:** `bundled` + `column_decltype`. The `bundled` feature compiles SQLite from source, which includes FTS5 by default — no additional feature flags needed. Verified by test.
2. **Schema embedding:** Used `include_str!("cache.sql")` to embed the schema at compile time. The file `cache.sql` was copied from `rose-py/rose/cache.sql` to `rose-rs/rose-core/src/cache.sql`.
3. **Lock implementation:** RAII `LockGuard` struct that holds its own `Connection` and lock name. The `Drop` impl deletes the lock row. The `lock()` function polls in a loop, sleeping until any existing lock's `valid_until` expires before retrying the insert.
4. **Connection setup:** Every `connect()` call sets `PRAGMA journal_mode=WAL`, `PRAGMA foreign_keys=ON`, and `busy_timeout(15000)` — matching the Python implementation. Uses `Connection::open()` with default threading mode (no `SQLITE_OPEN_NO_MUTEX`).
5. **Hash computation:** SHA-256 of the raw `cache.sql` bytes for `schema_hash`; SHA-256 of `serde_json::json!({...}).to_string()` for `config_hash` (mirrors Python's `json.dumps` approach).
6. **Database deletion:** On hash mismatch, the connection is dropped first, then the `.sqlite3`, `-wal`, and `-shm` files are removed before recreating.

### Deviations from Plan

- None significant. The implementation faithfully follows the Python source structure.

### Known Issues / Tech Debt

- The `config_hash` JSON serialization uses `serde_json::json!()` macro with `to_string_lossy()` for paths. This produces a deterministic hash but the JSON key ordering from serde_json's `json!()` macro is alphabetical, whereas Python's `json.dumps` preserves insertion order. This means the Rust config hash will differ from the Python config hash for the same config — but this is acceptable since the cache is always rebuilt from scratch when switching between Python and Rust.
- FTS5 is available via `bundled` without any extra configuration. If a future rusqlite version changes this, the `test_fts5_available` test will catch it immediately.
