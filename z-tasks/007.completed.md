# Task 007: Port rule_parser.rs (M-3.1)

## Objective
Port the rule parser DSL from Python to Rust, including all parse functions, type definitions, and the escaping protocol. This module is pure parsing logic with zero I/O.

## Context
Rose is a music library manager being migrated from Python to Rust. The rule parser defines a DSL for matching and transforming metadata tags. Rules consist of a matcher (which tags to search, pattern to match) and actions (replace, sed, split, add, delete). This module can run in parallel with audio tag work since it only depends on `common.rs`.

## Constraints Relevant to This Task
- **Regex flavor difference:** Rust `regex` crate uses `$1`/`${name}` for replacement syntax vs Python's `\1`/`\g<name>`. The sed action stores a compiled regex and replacement string — document the syntax change.
- Use `fancy-regex` if lookaround is needed, otherwise stick with `regex`.
- Port all 544 lines of test cases from `rule_parser_test.py`.

### 2. Design Decisions

- **Tag representation:** Used `type Tag = &'static str` (string-typed constants) instead of an enum. This matches the Python code's approach where tags are literal strings, makes serialization trivial, and avoids boilerplate for 31+ variants. The `ALL_TAGS` lookup table is an `&[(ExpandableTag, &[Tag])]` slice with longer keys ordered before shorter prefix keys to ensure correct greedy matching.
- **Regex crate:** Used the standard `regex` crate (already a dependency). No lookaround was needed by the parser itself, so `fancy-regex` was not required.
- **Error types:** `InvalidRuleError` and `RuleSyntaxError` are standalone structs (not `RoseError` variants) that implement `From<..> for RoseError` via `RoseError::Internal`. This keeps the error hierarchy clean and matches the Python pattern where these are subclasses of `RoseExpectedError`.
- **Display impls:** All types implement `Display` matching the Python `__str__` methods. `Rule::Display` uses a minimal `shell_quote` function that mimics Python's `shlex.quote`.

### 3. Deviations from Plan

- **Sed regex replacement syntax:** Documented in module-level doc comment and on `SedAction`. Rust's `regex` crate uses `$1`/`${name}` for capture-group references vs Python's `\1`/`\g<name>`. Users migrating rules must update their sed replacement strings.
- **Error message tag ordering:** The tag list in error messages follows `ALL_TAGS` iteration order (with specific `[role]` variants before their alias), which differs slightly from the Python order (Python iterates dict insertion order). The content is equivalent — all tags are listed.
- **Regex error messages:** The `sed:invalid[` test checks only that the error contains "Failed to compile the sed pattern regex" rather than matching the exact Python regex error text, since Rust's regex error messages differ from Python's `re` module.
- **`proptest` crate** added as a dev-dependency for proper fuzz testing.

### 4. Known Issues / Tech Debt

- The `RuleSyntaxError` Display does not include ANSI color codes (Python uses `click.style` for red caret). This is intentional for a library crate — color formatting should be handled at the CLI layer.
- `SedAction` implements `PartialEq`/`Eq` by comparing regex pattern strings, which is correct for testing but note that different regex strings can match the same language.
- `RELEASE_TAGS` contains a duplicate `releasetype` entry, faithfully ported from the Python source.
