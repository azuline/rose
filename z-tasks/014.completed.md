# Task 014: Cache Update — Directory Scanning and UUID Discovery (M-7.1a)

## Objective
Implement the first stage of the cache update pipeline: scan the music source directory, discover release directories, extract UUIDs from `.rose.{uuid}.toml` sidecar files, and create sidecar files for new releases.

## Context
Rose is a music library manager being migrated from Python to Rust. The cache update is a multi-stage pipeline that scans the music source directory, reads audio tags, and writes metadata to SQLite. This task implements stage 1 of 5. The stages are tightly coupled and form a single logical function — each stage's output is the next stage's input.

**Pipeline overview:**
1. **This task (014):** Scan directories → discover releases → output `Vec<ScannedRelease>`
2. Task 015: Compare mtimes → filter to changed releases
3. Task 016: Read tags → enrich with metadata
4. Task 017: Rename directories
5. Task 018: Batch SQL writes

## Constraints Relevant to This Task
- `.rose.{uuid}.toml` format is frozen: key names `new`, `favorite`, `rating` (-1 for null), `added_at` (ISO8601).
- UUID extracted by regex `^\.rose\.([^.]+)\.toml$` (from `STORED_DATA_FILE_REGEX`).
- In-progress directory detection: if a directory has NO `.rose.{uuid}.toml` but files have Rose release IDs, AND it's not `--force`, skip it (it's being copied).
- Directories named `!collages` and `!playlists` are excluded. Directories in `config.ignore_release_directories` are excluded.
- New releases get a UUID v7 (use `uuid` crate with `v7` feature).
- Preserve existing release ID from first audio file if available when creating new sidecar.

### Data structures for the pipeline

```rust
/// Intermediate: one scanned release directory.
pub(crate) struct ScannedRelease {
    pub source_path: PathBuf,
    pub release_id: String,           // extracted or newly created UUID
    pub files: Vec<PathBuf>,          // all files in directory (sorted)
    pub datafile_path: PathBuf,       // path to .rose.{uuid}.toml
    pub datafile_mtime: String,       // mtime as string
    pub is_new: bool,                 // true if sidecar was just created
}
```

### Functions

1. **`scan_release_directories(config, release_dirs: Option<Vec<PathBuf>>, force: bool) -> Result<Vec<ScannedRelease>>`**

   - If `release_dirs` is None, scan `config.music_source_dir` for all subdirectories.
   - Filter out `!collages`, `!playlists`, and `config.ignore_release_directories`.
   - For each directory:
     a. Walk the directory tree (`walkdir` or `std::fs::read_dir` recursive), collect all files.
     b. Sort files for deterministic order.
     c. Look for `.rose.{uuid}.toml` via `STORED_DATA_FILE_REGEX`. Extract UUID.
     d. Check if at least one audio file exists (suffix in `SUPPORTED_AUDIO_EXTENSIONS`). If none, record for deletion and skip.
     e. If no sidecar found:
        - Read first audio file's release_id via `AudioTags::from_file()`.
        - If release_id exists and not `force`: skip (in-progress directory). Log warning.
        - Otherwise: create sidecar with `StoredDataFile::new_default()`, UUID = file's release_id or new uuid v7.
     f. Record `datafile_mtime` from `os::metadata().modified()`.
   - Return `Vec<ScannedRelease>` and a `Vec<PathBuf>` of empty directories to delete from cache.

2. **`dirs_to_evict(config, release_dirs: &[ScannedRelease]) -> Vec<String>`** — collect source paths that have no audio files (for later SQL deletion).

### Data flow to next stage
The returned `Vec<ScannedRelease>` is passed to task 015's mtime comparison function. Each entry contains enough info to look up cached data and compare mtimes.

### Actual `ScannedRelease` shape

```rust
#[derive(Debug)]
pub(crate) struct ScannedRelease {
    pub source_path: PathBuf,      // resolved (canonicalized) absolute path
    pub release_id: String,        // extracted or newly created UUID
    pub files: Vec<PathBuf>,       // all files in directory (sorted), includes sidecar
    pub datafile_path: PathBuf,    // path to .rose.{uuid}.toml
    pub datafile_mtime: String,    // Unix timestamp as f64 string
    pub is_new: bool,              // true if sidecar was just created
}
```

Matches the spec exactly. The struct is `pub(crate)` and `Debug` only (no `Clone` needed for pipeline stage handoff).

### Function signature

```rust
pub(crate) fn scan_release_directories(
    config: &Config,
    release_dirs: Option<Vec<PathBuf>>,
    force: bool,
) -> Result<(Vec<ScannedRelease>, Vec<String>), RoseError>;
```

Returns `(scanned_releases, source_paths_to_delete)`. The `dirs_to_evict` function from the spec was folded into the main function — deletion candidates are collected inline (matching the Python approach where `upd_delete_source_paths` is populated in the same loop).

### Deviations from spec

- **`dirs_to_evict` not separate**: The deletion list is produced as the second element of the return tuple from `scan_release_directories`, rather than as a separate function. This matches the Python code's single-loop approach more closely.
- **No `walkdir` crate**: Used recursive `std::fs::read_dir` (via `walk_dir_recursive` helper) instead of adding the `walkdir` dependency, keeping the dependency footprint minimal.
- **Sidecar added to files list**: When a new sidecar is created, it is appended to the `files` list and re-sorted. This ensures downstream stages see the complete directory contents.

### Helper functions added

- `walk_dir_recursive(dir, files, release_id)` — recursively walks a directory, collecting files and extracting sidecar UUIDs via `STORED_DATA_FILE_REGEX`.
- `file_mtime_string(path)` — returns file mtime as a stringified `f64` Unix timestamp (matching Python's `str(os.stat(...).st_mtime)`).

### Data flow to task 015

The `Vec<ScannedRelease>` output provides everything task 015 needs for mtime comparison:
- `release_id` → key to look up cached release data in SQLite
- `datafile_mtime` → compare against cached `releases.datafile_mtime`
- `files` → iterate to check individual file mtimes against cached `tracks.source_mtime`
- `source_path` → detect source path changes
- `is_new` → new releases always need full processing (skip mtime check)
