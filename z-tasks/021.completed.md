# Task 021: Cache FTS Index (M-7.4)

## Objective
Implement the FTS5 full-text search index sync and the `process_string_for_fts` function that enables character-level substring matching. Register it as a custom SQLite scalar function via `rusqlite::Connection::create_scalar_function`.

## Context
Rose is a music library manager being migrated from Python to Rust. The rules engine uses FTS5 for fast substring matching across all track/release metadata. The trick: `process_string_for_fts` converts strings into character-separated tokens (using `¬` as separator), so FTS5 substring search becomes token prefix search. This is synced at the end of the cache update.

- The FTS table `rules_engine_fts` is already created by the schema (cache.sql). It has 21 columns.
- The FTS sync query is a 63-line 7-table JOIN (tracks, releases, releases_genres, releases_secondary_genres, releases_descriptors, releases_labels, releases_artists, tracks_artists).
- FTS rows are keyed by `t.rowid` (track rowid).
- We do NOT clean deleted tracks from FTS — the rules engine joins against `tracks` at use time, filtering them out. The cache is nuked often enough that space waste is acceptable.
- SQLite PRAGMAs on every connection.

### 1. `process_string_for_fts`
```rust
pub fn process_string_for_fts(input: &str) -> String {
    if input.is_empty() {
        return String::new();
    }
    // Join every character with ¬ separator
    // "hello" → "h¬e¬l¬l¬o"
    input.chars().map(|c| c.to_string()).collect::<Vec<_>>().join("¬")
}
```

This is Key Behavior #9 from the migration plan. The `¬` character is the FTS5 separator configured in the tokenizer, so each character becomes a separate token, enabling substring matching.

```sql
INSERT INTO rules_engine_fts (
    rowid, tracktitle, tracknumber, tracktotal, discnumber, disctotal,
    releasetitle, releasedate, originaldate, compositiondate,
    edition, catalognumber, releasetype,
    genre, secondarygenre, descriptor, label,
    releaseartist, trackartist,
    new, favorite, rating
)
SELECT
    t.rowid,
    process_string_for_fts(t.title),
    process_string_for_fts(t.tracknumber),
    process_string_for_fts(t.tracktotal),
    process_string_for_fts(t.discnumber),
    process_string_for_fts(r.disctotal),
    process_string_for_fts(r.title),
    process_string_for_fts(r.releasedate),
    process_string_for_fts(r.originaldate),
    process_string_for_fts(r.compositiondate),
    process_string_for_fts(r.edition),
    process_string_for_fts(r.catalognumber),
    process_string_for_fts(r.releasetype),
    process_string_for_fts(COALESCE(GROUP_CONCAT(rg.genre, ' '), '')),
    process_string_for_fts(COALESCE(GROUP_CONCAT(rs.genre, ' '), '')),
    process_string_for_fts(COALESCE(GROUP_CONCAT(rd.descriptor, ' '), '')),
    process_string_for_fts(COALESCE(GROUP_CONCAT(rl.label, ' '), '')),
    process_string_for_fts(COALESCE(GROUP_CONCAT(ra.artist, ' '), '')),
    process_string_for_fts(COALESCE(GROUP_CONCAT(ta.artist, ' '), '')),
    process_string_for_fts(CASE WHEN r.new THEN 'true' ELSE 'false' END),
    process_string_for_fts(CASE WHEN r.favorite THEN 'true' ELSE 'false' END),
    process_string_for_fts(COALESCE(CAST(r.rating AS TEXT), ''))
FROM tracks t
JOIN releases r ON r.id = t.release_id
LEFT JOIN releases_genres rg ON rg.release_id = r.id
LEFT JOIN releases_secondary_genres rs ON rs.release_id = r.id
LEFT JOIN releases_descriptors rd ON rd.release_id = r.id
LEFT JOIN releases_labels rl ON rl.release_id = r.id
LEFT JOIN releases_artists ra ON ra.release_id = r.id
LEFT JOIN tracks_artists ta ON ta.track_id = t.id
WHERE t.id IN (?,?,?) OR r.id IN (?,?,?)
GROUP BY t.id
```

## Completed

### Implementation Summary

All FTS5 functionality has been implemented in `rose-rs/rose-core/src/cache.rs`:

1. **`process_string_for_fts(input: &str) -> String`** (public): Converts a string into character-separated tokens using `¬` (U+00AC) as separator. `"hello"` becomes `"h¬e¬l¬l¬o"`. Empty input returns empty string.

2. **`register_fts_function(conn: &Connection)`** (private helper): Registers `process_string_for_fts` as a custom SQLite scalar function via `rusqlite::Connection::create_scalar_function()`. Handles NULL SQL values gracefully by returning empty string.

3. **`sync_fts_index(conn, track_ids, release_ids)`** (pub(crate)): Deletes old FTS rows for affected tracks, registers the custom function, then executes the 7-table JOIN INSERT query matching the Python implementation. Called at the end of `batch_write_releases`.

### Rusqlite Feature Flags

Added `"functions"` to the rusqlite features in `Cargo.toml`:
```toml
rusqlite = { version = "0.31", features = ["bundled", "column_decltype", "functions"] }
```
- `bundled`: Provides FTS5 support via the bundled SQLite build.
- `functions`: Required for `create_scalar_function()` API.

### Deviations from Python FTS Query

1. **NULL handling**: The Rust custom function handles NULL SQL values (returns empty string), whereas Python's `create_function` would receive `None`. This is needed because columns like `r.releasedate`, `r.originaldate`, `r.compositiondate`, `r.edition`, `r.catalognumber` can be NULL.

2. **Integer columns**: `t.tracktotal` and `r.disctotal` are wrapped with `CAST(... AS TEXT)` since they are INTEGER columns and the custom function expects text input.

3. **No DISTINCT in GROUP_CONCAT**: The Python code uses `GROUP_CONCAT(rg.genre, ' ')` without DISTINCT. SQLite does not support `GROUP_CONCAT(DISTINCT col, separator)` with a separator argument, so this matches the Python behavior exactly.
